# RDP download helper

Ship a first slice for the observed F5 BIG-IP access portal. The toolbar popup provides an on-by-default switch. Per-site setup is explicit. From the signed-in desktop page, save the visible label of the desktop to download. That stores only the HTTPS origin, page path, and label locally and asks for permission on that origin plus optional Chrome download access. Employer-specific settings are empty in the distributed build and do not sync.

The feature owns browser listeners, portal DOM actions, and separate feature state. Workspace only renders the card. The worker checks the active tab when it loads or becomes focused on the configured HTTPS origin. At the signed-out screen, the helper recognizes the explicit session-finished text and the same-origin new-session link. It restarts the flow whenever that page is active, including after previous recovery. Switching away pauses browser actions. Returning resumes the visible step and can use a form that Bitwarden already filled. An existing Microsoft session can take F5 straight to the authenticated desktop page, where the configured download starts independently of the Microsoft screens.

With a locally saved work email and optional access to Microsoft's sign-in origin, the helper can select one exact match on Microsoft's account picker in a tab that the helper is already tracking through portal sign-in. The picker check ends when the account is selected, the page is left, or five seconds pass. Forms and verification still use the user's normal sign-in. Bitwarden can autofill the F5 form as configured. On Microsoft, the optional desktop helper invokes Bitwarden with Ctrl+Shift+P on the username and password screens when shown. The user completes their chosen verification method.

Only the exact configured desktop control on the observed webtop path can start a download. Late-rendered controls are watched for up to ten seconds using page events. Page navigation tears down observation. The worker rechecks configuration and access before clicking and uses the inspected document ID. Chrome download state confirms the resulting file using the expected portal origin, webtop referrer, file extension, and a bounded time window. Chrome does not expose a download tab ID, so one request per portal can be pending and a concurrent manual download of an RDP file from the same authenticated page may be indistinguishable. The helper does not retry a download whose outcome is uncertain.

When a top-level F5 RDP launch URL on the configured origin returns HTTP 403 or renders Chrome's own error page, the helper returns to the portal home when that tab is active. An ordinary launch response stays on its normal path. Recovery uses tab-completion and activation events and the portal permissions. The same manual sign-in and MFA handoff applies before another download can start.

The popup can remember the user's choice to acknowledge the F5 monitoring notice automatically. The choice is local to one HTTPS origin and can be set from the notice page before a desktop is configured. On completed loads, the helper checks that the rendered notice includes the expected monitoring language and offers a unique visible same-origin acceptance link alongside a decline link. Pages that fail these checks stay on screen. The download permission is needed only for the file workflow.

The optional F5 form submission waits up to 20 seconds for Bitwarden to fill the recognized Secure Logon form on that portal. It checks only whether the fields are populated and uses the page's Logon control on the same document. Manual typing, navigation and an unrecognized form hand control back to the user. Each portal run makes at most one automatic submission. Microsoft verification remains manual.

An unconfigured or disabled helper ignores tab loads after the initial settings read. There is no polling or always-on page content script. The live workflow's nonstandard signed-out variants and exact desktop control still need a user-assisted run. The packaged fixture uses a simulated HTTPS portal and sign-in handoff, with permissions granted in its disposable manifest. It covers disabled behavior, repeated sign-out recovery on activation, cached Microsoft sign-in, manual policy acceptance, delayed portal readiness, download confirmation, reload deduplication, and rejection of ambiguous controls. No new runtime package was added for the fixed local configuration shape.

The current build targets the observed F5 portal pattern. Any Chrome Web Store scope discussion belongs in feature admission before publication.

The before-and-after popup benchmark used 15 loads each on the IdeaPad with Chromium 153 and an unconfigured helper. Warm median moved from 78.1 to 86.9 ms and warm P95 from 92.1 to 103.9 ms. Neither increased by both 20% and 20 ms. The benchmark measures the ordinary popup, and the simulated portal test separately verifies event-driven readiness and download completion.
